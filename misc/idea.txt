These are ideas about stuff that might or might not be implemented in
future; when they are implemented they might not be done exactly as
specified here, since the plans may change in future. (Some might be
decided against adding in future, or in a more limited way than is
described here; other changes may also be made.)


=== Text compression ===

A compression for the script text in GLOBAL and *.BRD lumps may be made in
future. The code 0x00 is not valid within the text, so it can be used as a
prefix for compression codes.


=== Custom fonts ===

This is a new idea of a custom font format, different than what was
mentioned here before. (The .CHR format of MegaZeux could also be supported
but only for 8x14 fonts with no animations and no other features.) It could
be a DER-based format with:

* First character code (integer): For a full font this will be zero; for
a partial font it can be any number in range 0x00 to 0xFF.

* Number of character codes (integer): For a full font this is 0x100 but
for a partial font it is less than 0x100. If it is a wide font then this
number is usually more than 0x100.

* Text direction (enumerated, optional)

* Font data; this field is normally a implicit typed sequence, where the
type number specifies the type of font data; see below.

The further fields are optional and if one is not present but a later one
is present, the null should be used in place of the omitted one.

* Character code mappings (set)

* Animations

* Case folding (octet string)

The format of the font data can be:

* Type 0 = A fix pitch font with a width of eight pixels, and one bit per
pixel. A sequence with a integer being the font height (normally fourteen)
and then a octet string with the raw raster data of the font.

* Type 1 = (May be used like type 0 but with compressed raster data.)

Character code mappings is a set where most kind of items will be implicit
typed strings but some will use ordinary types instead. They are:

* Integer = IBM code page number (or extended code page number).

* Object identifier.

* Type 0 = TRON code mapping.

* Type 1 = IANA character set name, as used in "text" MIME types.

* Type 2 = XLFD character set name, which has a single hyphen.

* Type 3 = ISO 2022 escape codes to select the character sets.

There cannot be more than one wide font. Wide characters always have the
first byte in range 0x80 to 0xFF and the second byte in range 0x10 to 0xFF.
(These restrictions would apply to Super ZZ Zero, but if other programs use
this font format they might not have this restriction.)

Also, not everything supported by this format will necessarily be supported
in Super ZZ Zero, at least at first; some might be ignored and some things
might not be used in Super ZZ Zero.


=== Custom palettes ===

This could be done like MegaZeux, by .PAL lumps. (With enhanced graphics,
this could also be used with more than sixteen colours; there could be
sizes of 16, 32, 64, or 128 colours.) (It might also be suitable to have
VGA palettes (three bytes per entry, like MegaZeux) and EGA palettes (one
byte per entry), so that EGA can be used for smaller files when you do not
want the VGA. It is not necessary to mark this (or the number of colours)
somewhere explicitly; it can be determined from the lump size.)

VGA format:  00rrrrrr 00gggggg 00bbbbbb
EGA format:  00rgbRGB

The ability to enable/disable flashy text should also be added (this might
be one of the text mode options in addition to SMZX mode; see the below
section about enhanced graphics).


=== Music ===

For music lumps, there are some features I dislike of MOD/S3M/XM/IT even
though it is good idea to have instruments and notes. Specifically:

* Such formats assume 12-TET; they are not very good for just intonation
and stuff like that.

* They must be arranged in patterns and orders; this is not always the
best way for MML conversion.

* There are some features that should not be necessary for play back;
some of these (e.g. song title and some comments) may still be useful
to keep, but such things as note ranges per instrument are probably
not needed since the MML compiler can handle these.

However, it would be good for possibility to convert MOD, S3M, XM, IT
(and possibly others, e.g. Reality Adlib Tracker) into the format which
can be used for this, in case you want to use existing editors, and that
many of the existing effects can be available. However, a MML compiler
specifically for this format can also be made up.


=== User preferences ===

These user preferences are those which do not directly affect the game
engine (although the default values may sometimes be based on them), but
can be used in game worlds to control various features, such as:

* Want reduced animation

* Auto/ask to skip cutscenes

* Puzzle difficulty

* Language

* Using keyboard or joypad

* Want to censor certain things (e.g. swearing)

* Visual indication of sound

There can be a field in GENERAL.DER to specify which such preferences are
used by this world, what values they can have, and their defaults (which
may be fixed and/or automatic). There can then be a opcode which can be
used to access this information.

The field in GENERAL.DER could contain a sequence for each user preference;
these are numbered starting from zero. You can put null in place of one of
these sequences if that number is not used (e.g. if it was used in the past
but now has been removed). Each of these sequences contains:

* The OID of the preference.

* An optional PC string which labels the preference.

* The default value, which is a integer. (The OID of the preference might
also allow the game engine to provide its own default value, e.g. for
whether or not sound is enabled.)

* A boolean to indicate whether or not it is allowed to be changed after
the game has started. Even if this is false, it can still be changed before
the first time it is read by the INFO opcode; it will record in the save
game file whether or not this occurs, and what the saved values are.

* Further data are for the possible values that it can have.

For each possible value that it can have (where the values are numbered
starting from zero), it has (these are not inside of their own sequence,
but are inline in the "preference item" structure):

* The OID of the value. If it is relative, it is relative to the OID of
the preference. Alternatively this can be a set of OIDs; all of these OIDs
are interpreted in the same way for this specific world (even if their
meanings are otherwise distinct).

* An optional PC string which describes this possible value.

Nulls may intervene to mean that a number is not used.

A new opcode could be INFO which takes the number from the second operand
and the value (according to the above) is written to the first operand.
If the second operand is negative then it could correspond to various
kinds of built-in information which does not use this.


=== Item window ===

The item window is meant for a kind of inventory menu.

Opcodes related to item memory and item windows:

* IMNU = Display the item window, and request selection of an item. Flags
can be used to allow/disallow/force sorting and to allow/disallow items
to be discarded. You can also restrict display by classes of items.

* IGIV = Give a specified quantity of a specified item.

* ITAK = Take a specified quantity of a specified item.

* ICNT = Count how many of a specific item you have (or of all items that
have a specific quality or are in a specific class). Can also be used to
total the value of a specific field (e.g. mass) of items.

New commands to be used in scripts might also be made for working with item
memory, such as #GIVEITEM and #TAKEITEM and #ASKITEM.


=== High scores ===

There can be an optional high score file; the user configuration file could
be used to enable or disable this feature.

The format of the high scores could be specified in GENERAL.DER, which can
specify things to be included in high score entries and how they will be
sorted and classified; they are not necessarily limited to only the score,
but also such things as difficulty level, achievements, etc.

There can be a opcode called HISC to write new entries into the high score
file (reading from the high scores is deliberately not possible).


=== Editing history ===

This means optionally storing the editor version history (the user
configuration file can control what is stored) in the world file. I am
not really sure if this is useful, although OHRRPGCE does something
similar (but unlike OHRRPGCE, a separate lump (e.g. HISTORY.DER) should
be used which is not used for other purposes).


=== Screen transition animations ===

For defining screen transition animations when going between boards, or
when open or closing a text window or item window (or other screens, if
custom screen displays are possible).

This should be possible for the user to override by the configuration file.
This would be done by options named "board_anim" and "window_anim", whose
values can be zero to use the time specified in the world file, positive
for the specified number of milliseconds per frame, or negative to limit
the total duration of the animation to not greater than the specified
number of deciseconds. The default values will be zero, allowing the values
specified in the world file to work.

Each screen can have an associated transition animation, perhaps numbered
from 0 (meaning no animation) to some number (one less than a power of
two), such as 15 or 63.

The transition animations themself can be defined in a lump called
TRANSIT.DER, containing a sequence of the definitions, with 1-based
indexing. Each definition can have the fields:

* Total number of animation frames, which is an integer.

* Optionally, another integer for the number of milliseconds per frame.
If this is omitted, the current game speed is used. (Either way, it can be
overridden by the user configuration file.)

* The effect. This can be a implicit typed sequence, or it can be a single
Set (for multiple simultaneous effects) or Sequence (for multiple effects
that are done in sequence).


=== Enhanced graphics ===

Super ZZ Zero is and will continue to be primarily emulating PC text mode
instead of having enhanced graphics, although it might be possible in
future to add enhanced graphics modes, with the ability to run at the same
time as the emulated text mode graphics. Each cell of the text grid has a
VF_FRONT flag, which can be used to display it in front of the graphics
(which causes the graphics layer to be obscured); if not set then it is
displayed behind the graphics and may be obscured by the graphics.

One possible idea is to make a slice tree like OHRRPGCE has, although we
probably should not need all of the features that OHRRPGCE has. (Slice
trees could be DER-encoded lumps whose names have a .EGS suffix (which
stands for "Enhanced Graphics Screen").)

One component of the slice tree can be the board view; one of the mode
flags of stats can be used to display them as sprites in a separate layer,
and the board view component will be able to specify a sprite offset,
which will allow sprites to be displayed partially in front of walls.

Other possibility is SMZX mode like MegaZeux does (this can be used as an
optional mode for the text grid layer; when combined with 40-columns mode
then it might be a vertical SMZX mode).

Some worlds might support enhanced graphics as an optional feature.
(It can be specified as mandatory or optional in GENERAL.DER.)


=== Custom windows ===

In addition to text windows and item windows, it might be possible to use
screens as custom windows.

My idea is to add a opcode for displaying a custom window, which can be any
defined screen, and to specify the subroutine to execute while the custom
window is active.

Maybe it should also be possible to have custom printing for custom
windows, that if you push F11 then it can customize the text to print.


=== Other instructions ===

SQRT can be used for calculating square roots.

DICE might be added for more sophisticated random numbers.

EXT0, EXT1, etc can be used if too many opcodes are defined, that these can
then be used for further extended opcodes. (Perhaps, those that are going
to be less common, or need an additional operand, might use these.)


=== Zones ===

These zones are meant to be like a combination of the rotation zones in
ZZ Zero and the zones in OHRRPGCE. The number of zones per board probably
does not have to be very large; eight might be sufficient (allowing one
byte to specify a set of zones to select).


=== Script subroutines ===

This feature is implemented now, although possibly it may be improved.

*Q would add the message to a queue if it is currently locked; it will be
called once the subroutine stack is empty.

*S would cause a received message to be received by the first unlocked
instance rather than all of them.


=== Script states movable between boards ===

Currently, there is only one global script whose states can be movable
between boards, and only stat 1, and only if stat 1 does not already
have a script in that board.

However, maybe it might sometimes be wanted to do more than that.


=== Visibility ===

An idea is to implement blocking visibility. (However, this might also be
done by use of program codes within the world file, so it is not really
necessary to implement within the game engine directly, although doing so
may be helpful anyways for some reasons.) Tiles might then be set as
blocking visibility or as not blocking visibility, so that you cannot see
past a opaque wall, and you can see past windows even if you cannot walk
past windows.


=== Wrap around ===

Allowing boards to wrap around, by the use of a new board flag (or possibly
two flags, one for north/south and one for east/west).

The game engine does not currently expect this and will need modifications
to support this properly, although the file format probably doesn't need to
be changed. Some of the things that must be changed include:

* Anything involving directions

* The general_move function

* Scrolling and display

* Line joining


=== Regression testing and demo recording ===

Some way to do regression testing, sort of like Free Hero Mesh. Note that
Free Hero Mesh is meant to be fully deterministic, while Super ZZ Zero
isn't (and isn't meant to be). It might be necessary to include testing
of features other than the game engine too.

Demo recording might also be suitable; the same functions can be used for
regression testing than demo recording and playback. A demo recording can
store the random numbers and other details needed to repeat (since future
versions might change the working of the random number generator, and the
existing random numbers should be saved for use with demo recording and
for testing). If demo recordings can include assertions, that will help.


=== RPG battle mode ===

This feature has been mentioned in the document of ideas of features to
implement in future for ZZ Zero. (This is probably not a high priority.)


=== Save game upgrading ===

Currently, a save game can only be used with the same version of the world
file that was used to play the game. A new lump called UPGRADE.DER could
be made in order to allow using old save games with new world files in some
circumstances, making the save game upgraded to use the new world file.


=== Board editor features ===

Some ideas about board editor features. (Some of these may also be suitable
for the screen editor.)

* Import/export MZM: Only layer mode MZM is relevant for Super ZZ Zero.

* Import/export other formats: ANSI, XBIN, etc. This may also include user
configuration options for whether or not to import/export SAUCE. It might
also be possible to specify external programs for converting other formats.

* Undo/redo

* World map


=== Text editor features ===

Ideas about text editor features.

* Block selection: Commands to set a beginning and ending of a block; you
can then use other block commands to make copies of it, to delete it, or
to move it.

* Using external programs to process text: Text can be filtered through
an external command for processing; it will be sent to that program's
stdin and then the text is replaced by the stdout from that program.

* Undo/redo

* Find and replace

* Auto-complete: If it is implemented, then it should also be possible to
disable this feature, and might be disabled by default.


=== Versions ===

There is also the consideration of working with non-released versions. One
idea is that non-released versions would add something into the optional
set in GENERAL.DER to mention this, and then a warning message will be
displayed when running with a released version (non-released versions will
not display the warning message for this case).


=== Scroll lock ===

An idea is to have a setting for the scroll lock key to affect the function
of the arrows, to scroll the view in some editors and some menus. However,
due to limitations in SDL, this is not implemented yet.


=== Undesirable features ===

There are some features which will probably be permanently out of scope
(or that are bad in general), and that I am unlikely to want to add (even
if someone provides a patch). Some of these features include:

* Password protection. (MegaZeux used to have this feature, and OHRRPGCE
still does (although I think some maintainers want to remove it).)

* RTC (date/time) access.

* File I/O. (It may be possible to support lump I/O, but the codes in the
world file would never be able to access external files. External file
access is always under the control of the user.)

* In app purchases.

* Unicode.

* Network access. (Communication with catalog services, version control
services, etc, would use separate programs, and are not a part of the
game engine itself.)

* Full keyboard access. (Many keys will be reserved by the game engine
and/or operating system and/or window manager. The keys that can be used
can use an abstract handling.)

* Automatic updates. (I dislike automatic updates, and if someone wants to
use them it would be done by a separate package manager instead, which
should allow the user to disable automatic updates, anyways.)

* Operating system detection.

* Saving/restoring games by scripts/programs defined in the world file.
(Restrictions for saving games may be added, but not restrictions for
restoring saved games.)

* Persisting data across different instances of a game. (Data will always
persist across save/restore games, but if you restart the game and create
a new save file, it does not interact with the old save file at all.)

* 3D graphics.

* Ability for game world code to adjust game speed at run time. (I may add
a setting within the world file to specify the default game speed, though.)

* True colour graphics.

* Multiplayer mode.

(Some of these are not entirely certain, though.)
